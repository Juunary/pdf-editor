## 1. 요약

- 저장 힙 계수 모델 `step-v1` 을 `decideSaveMethod`·`planSave` 에 넣었다. 예상 피크 = max(현재 힙, min(필요량 × 1.2, 필요량 + 96 MiB)), 필요량 = max(현재 힙, 기본 + 저널) + 저장 증가분.
- `step-v2`(M5 리뷰 H1, 4.4): 필요량의 "현재 힙" 을 "사용 중 힙" 으로 바꿨다. 첫 저장은 현재 힙 그대로(계수·저장 1회 결과 불변), 직전 저장이 있으면 그 저장의 사용 추정 + 저장 뒤 늘어난 힙. 두 번째 저장부터 저장 전 MuPDF 자원 캐시를 비운다. 같은 세션 저장 2회 312회 측정에서 미탐 0, 과탐(문서 기준) 전체 0/14·증분 1/17. 525 MiB 문서 재현: 두 번째 저장 예상 2,279 MiB over-limit → 1,404 MiB ok(실측 898 MiB).
- 저장 증가분 = 고정분 + 객체 수 × b + 원 스트림 바이트 × c + 객체 크기 × e. 객체 크기 = (입력 − 원 스트림) + 객체 스트림을 푼 크기.
- 검증(서버 Node, 304회 측정, 문서 단위 leave-one-out): 미탐 0/152(전체 저장)·0/152(증분). 과탐은 문서 기준 0%(전체)·5%(증분), 시나리오 기준 15%·48%(4.1 해석 참조).
- 이전 배율 모델(입력 × 3.48·2.98)은 같은 데이터에서 미탐 106/152·108/152. 실제 문서 대부분을 과소 추정했다.
- 대용량 합성 대체 2건(검증 전용): Node 16회·Chrome Worker 4회 미탐 0. Chrome Worker 9회 전체 미탐 0, 탭 크래시 0.
- 발견 3건(코드 수정함): (1) Worker 번들에서 `wasmHeapBytes` 가 null 이라 planSave 가 늘 배율 모델로 떨어지고 있었다(4.3). (2) 통계 계산을 예산에서 끊어 앞쪽 객체만 읽어 두면 뒤이은 저장 피크가 284 → 1,389 MiB 로 뛴다(2.3). (3) 고정 간격 표본은 객체 배치 주기와 맞물려 한 종류를 통째로 놓친다(원 스트림 66.7 → 0 MiB, 2.4).
- D4: 같은 블록 반복 편집은 저널이 늘지 않고(100회 +0 MiB), 서로 다른 문단을 처음 고칠 때마다 그 쪽 콘텐츠 크기만큼 는다(8.9 MB 쪽 문단 45개 +380 MiB, 추정 383.5 MiB). 재적용 시간은 1.2 MB 쪽 100회 43–49 s 로 체크포인트 기준(2 s)을 넘는다. 재적용 실패 2건 발견(5절).
- 지원 크기 상한 안내 값 `SUPPORTED_INPUT_BYTES` = 790 MiB(이미지 위주 문서, 열자마자 편집 후 전체 저장 기준).

### 2.3 발견: 힙 피크는 저장 전 이력에 따라 계단식으로 달라진다

| 문서(전체 저장) | 보기 0 | 보기 3 | 보기 10 | 보기 30 |
| --- | --- | --- | --- | --- |
| synth-image-900 | 938 | 1,349 | 1,370 | 1,430 |
| synth-image-700 | 938 | 642 | 663 | 724 |
| synth-image-1100 | 1,998 | 실패 | 실패 | 실패 |

(MiB) 같은 문서·같은 편집도 저장 출력 버퍼가 제자리 확장되는지, 새 블록으로 복사되는지(이전·새 버퍼 공존)에 따라 피크가 1.5배까지 달라진다. M0 의 900쪽 Stream 1,681 MiB(`docs/m0-dod-xobject-redact-save.md` 3.3)와 이번 938 MiB 의 차이도 같은 원인으로 본다. 모델은 시나리오 최대를 덮어야 하므로 시나리오마다 표본을 둔다.

발견: 통계 계산의 부분 적재가 저장 피크를 바꾼다(합성 객체 2,000쪽, 전체 저장, 보기 10쪽).

| 저장 전 객체 적재 상태 | 저장 피크 MiB |
| --- | --- |
| 통계 계산 안 함 | 304 |
| 전수 적재 | 341 |
| 앞쪽 번호 10만·25만 개만 적재 | 1,389·1,381 |
| 간격 2·5·50 적재 | 284·284·304 |

- 처음 구현(앞에서부터 세다 1 s 예산에서 멈추고 나머지를 간격 표본)은 병렬 측정에서 이 상태를 만들었다(보기 10·30 에서 1,444·1,436 MiB).
- 바꾼 방식: 64개 구간마다 하나씩 먼저 훑어 객체당 시간을 재고, 전수 예상이 예산(1 s) 안이면 전수, 넘으면 예산에 맞춘 층화 표본(`approximate: true`, 2.4). 같은 문서 보기 0·10·30, 예산 100·1,000 ms 6회 284–341 MiB, large-object-4000 3회 595–678 MiB.
- 원인(MuPDF 내부 할당 순서)은 확인하지 않았다. 제품 사용 중 다른 경로(검색·추출)가 비슷한 부분 적재를 만들 가능성은 남는다(9절).

### 2.4 문서 통계 계산 시간·힙·표본

| 대상 | 시간 ms | 힙 증가 MiB | 방식 |
| --- | --- | --- | --- |
| 코퍼스 24건 | 중앙 13, 최대 83 | 0 | 전수 |
| 합성 이미지 100–1,200쪽, large-image-mixed | 3–102 | 0 | 전수 |
| synth-object-500(객체 12.6만) | 234–448 | 23.8 | 전수 4·표본 4(동시 8프로세스 부하에 따라) |
| synth-object-1000·2000(객체 25만·50만) | 319–588 | 23.2·49.3 | 표본 |
| large-object-4000(객체 102만) | 640–780 | 57.1 | 표본 |

- 표본: 객체 번호를 `stride` 개 구간으로 나눠 구간마다 고정 시드 의사난수 위치 하나를 읽고 구간 크기를 곱한다. 처음 구현(구간 첫 객체)은 large-object-4000 에서 객체 배치 주기(쪽마다 254개)와 간격(64)이 맞물려 콘텐츠 스트림을 하나도 고르지 않았다(원 스트림 0 MiB, 전수 66.7 MiB). 층화 표본은 66.1 MiB.
- 표본은 큰 스트림 몇 개(폰트 파일 등)를 놓치면 원 스트림 합을 크게 줄여 본다(시험 문서: 전수 4.16 MB, 표본 0.02 MB). 그래서 `approximate` 이면 모델은 원 스트림 = max(표본 값, 입력 크기)로 계산한다. 이 보정은 (입력 − 원 스트림) 몫을 객체 크기 계수(1.58)에서 원 스트림 계수(2.43)로 옮겨 그 몫만 키우고, 객체 스트림 푼 크기는 덮지 않는다(정정: 처음 기록의 "예상이 커지는 쪽" 은 객체 스트림 몫에는 맞지 않았다, M5 리뷰 M1).
- 객체 스트림 푼 크기는 표본과 무관하게 전수로 센다(M5 리뷰 M1, 4.5): 원본 바이트의 xref(전통 표·xref 스트림, /Prev·/XRefStm 사슬)에서 압축 객체가 든 객체 스트림 번호를 모아 그것만 하나씩 풀고 놓는다. xref 를 읽지 못하면(복구한 문서 등) 객체 스트림 번호를 모르므로 예산과 무관하게 전체를 전수로 센다.
- 객체 스트림 디코드는 그 스트림만 하나씩 풀고 바로 놓는다(nasa-se-handbook 34 ms). 계약 D5 의 "디코드 합산 580 ms·+73 MiB" 는 모든 스트림을 푼 값이라 다르다.
- 힙 증가는 객체를 읽어 둔 비용이다. 저장이 어차피 모든 객체를 읽으므로 그 몫이 현재 힙(모델 H)으로 옮겨 갈 뿐이다.

## 3. 모델

### 3.1 식

```
H      = max(현재 wasmHeapBytes, 기본 + 저널)            기본 = 열기 직후 WASM 힙, 저널 = journalBytes(5절)
inc    = d + b × 객체 수 + c × 원 스트림 + e × 객체 크기    객체 크기 = max(0, 입력 − 원 스트림) + 객체 스트림 푼 크기
need   = H + inc
예상   = max(현재, min(need × 1.2, need + 96 MiB))         emscripten 힙 확장 규칙(현재 × 1.2, 요청 + 96 MiB 이하)
수준   = 예상 > 상한 → over-limit, > 상한 × 0.75 → warn, 그 밖 ok   상한 2,048 MiB
```

### 3.2 계수(`packages/pdf-ops/src/save-method.ts` `SAVE_HEAP_COEFFICIENTS`)

| 경로 | d(고정분) | b(객체 1개당) | c(원 스트림 byte당) | e(객체 크기 byte당) | 입력 byte당 |
| --- | --- | --- | --- | --- | --- |
| 전체 | 8.2 MiB | 420 B | 2.43 | 1.58 | 0 |
| 증분 | 0 | 440 B | 2.57 | 1.65 | 0 |

산정(`tools/bench/heap-fit.mjs`, 형태 `lp/objbytes/step+d/prior`):

1. 선형 계획: 적합 표본(대용량 대체 제외, 경로별 144개, 표본 통계는 원 스트림 = 입력으로 바꿔 넣음) 전부를 덮는다는 제약(미탐 0) 아래 상대 과대 추정 합(Σ 예상 증가분 ÷ 측정 피크)을 최소화, 계수 ≥ 0.
2. 객체형 계수 하한(사전값): b ≥ 400 B, e ≥ 1.5. 객체 크기 신호가 큰 문서가 nasa-se-handbook 하나뿐이라(압축 객체 스트림 0.38 MiB → 풀면 18.4 MiB) 그 문서를 빼면 e 가 0 으로 떨어져 LOO 미탐이 났다. 하한은 전체 측정에서 본 객체당·객체 바이트당 증가분의 대략 값이다.
3. 안전 여유: 증가분 × KS + AS. LOO 미탐 0 을 만족하는 조합(KS 1–1.5, AS 0–48 MiB) 중 과탐이 가장 적고 평균 예상/측정이 가장 작은 것: 전체 KS 1.05·AS 4 MiB, 증분 KS 1.1·AS 0. 여유를 LOO 결과로 골랐으므로 LOO 수치는 여유 선택에 쓰인 값이다.
4. 코드 값은 위 결과를 올림했다(올림은 예상을 키우는 쪽이라 미탐을 만들지 않는다).

선형 계획 계수(여유 전): 전체 d 3.99 MiB·b 400·c 2.312·e 1.500, 증분 d 0·b 400·c 2.336·e 1.500.

### 4.1 미탐·과탐 정의와 해석

- 미탐: 표본(문서·저장 경로·보기 시나리오)마다 측정 피크 > 예상 피크. 측정 실패는 예상이 over-limit 이 아니면 미탐(예상이 상한 이하인데 실패).

### 4.4 같은 세션 저장 2회(M5 리뷰 H1)

문제: WASM 선형 메모리는 줄지 않는다. `step-v1` 은 첫 저장 뒤 커진 힙(저장이 쓰고 놓은 출력 버퍼 등)을 "현재 힙 = 사용 중" 으로 보고 그 위에 증가분을 다시 더했다. 재현(합성 이미지 700쪽, 525 MiB, 편집 후 전체 저장 2회, 저장소 밖 재현 스크립트, 문서는 `tools/bench/synth.mjs`):

| 저장 | 저장 전 힙 MiB | `step-v1` 예상 | `step-v2` 예상 | 실측 피크 MiB |
| --- | --- | --- | --- | --- |
| 1회째 | 22 | 1,404 ok | 1,404 ok | 898 |
| 2회째 | 898 | 2,279 over-limit | 1,404 ok | 898 |

식(`step-v2`, `estimateSaveHeapModel`·`usedHeapAfterSave`):

```
사용 중 = 현재 힙                                             (이 세션에 저장이 없었을 때, step-v1 과 같음)
사용 중 = 직전 저장의 사용 중 + max(0, 현재 힙 − 직전 저장 직후 힙) (직전 저장이 있을 때)
need   = max(사용 중, 기본 + 저널) + 증가분
예상   = max(현재 힙, min(need × 1.2, need + 96 MiB))
```

- 직전 저장이 읽어 들인 객체는 힙에 남지만 그 몫은 직전 저장의 증가분이 이미 덮었다(같은 증가분을 다시 쓴다).
- 저장 뒤 렌더가 저장이 놓은 빈 공간 안에 자원 캐시(풀린 이미지·글꼴)를 쌓으면 힙 크기는 그대로라 사용 중 추정이 놓친다. 1차 측정(v1, 캐시 비우기 없음)에서 코퍼스 2건이 미탐이었다: kogl-nabo-rnd107 증분 보기 30(예상 56, 실측 66 MiB), zen-beamer-7535020 증분 보기 30(예상 93, 실측 104 MiB). 그래서 두 번째 저장부터 저장 직전에 `mupdf.emptyStore()` 를 부른다.
- 첫 저장 전에도 비우는 방식(v2)은 저장 1회 미탐 6건을 만들었다(합성 이미지 900쪽 전체 보기 10: 1,370 → 1,924 MiB, 빈 조각 때문으로 본다). 첫 저장 전에는 비우지 않는다(v3, 채택).

## 5. 저널 상한(D4)

### 5.1 저널 보유 추정

- `EditEngine.journalBytes`: 커밋한 작업마다 pdf-ops `changedObjects`(바뀐·새 객체, 편집 블록 포함) 중 스트림의 /Length 합을 기록하고, undo·redo 목록에 있는 작업의 합을 돌려준다. 새 편집이 redo 를 버리면 그 비용도 빠진다. 재적용한 편집(복구)은 저널 밖이라 세지 않는다.
- 사전 /Length 만 조회한다(스트림은 읽지 않음). 계약 D4 "WASM 조회 없음" 과 다르다: JS 쪽에 교체 스트림 길이가 없고(pdf-ops 가 쓰기를 맡음) 객체 몇 개의 사전 조회라 비용이 작다.
- 처음 고치는 문단은 쪽 콘텐츠 + 새 블록, 이미 편집한 블록을 다시 고치면 그 블록만 든다. 처음 구현(작업마다 쪽 콘텐츠 /Length)은 같은 블록 100회 편집에서 118 MiB 로 추정했으나 실제 힙은 22 MiB 그대로였다.

### 5.3 판정·권고

- 판정(구현): `journalAdvice(method, size)` = 저널 추정 + 예상 저장 증가분 > 경고선(= `HEAP_WARN_FRACTION` × 상한 = 1,536 MiB)이면 `advised`. 같은 조건이면 planSave `heap.message` 끝에 "되돌리기 기록이 약 N MiB 를 쓰고 있습니다. 저장한 뒤 문서를 다시 열면 줄어듭니다." 를 붙인다. `PdfSession.journalAdvice()` 로 뷰어가 커밋 뒤 물을 수 있다(현재 RPC 에는 없음, 8절).
- 단계 수 상한: 두지 않는 것을 권고한다. 근거: 저널 비용은 단계 수가 아니라 처음 고친 쪽의 콘텐츠 크기에 비례하고(같은 블록 100회 +0), MuPDF 에 오래된 단계를 버리는 API 가 없어 상한을 둬도 메모리를 줄일 수 없다(넘으면 저장 후 다시 열기뿐).
- 체크포인트: 재적용 시간 기준(2 s)을 1.2 MB 쪽 5건 안팎, 8.9 MB 쪽 1건에서 넘는다(1.2 MB 쪽 500건 312 s). 계약 D4 조건상 도입 대상이다. 다만 재적용은 Worker 복구에서만 쓰이고(저장 실패·wasm 트랩), 비용은 편집 판정·레이아웃 재계산이다. 결정은 메인 세션(8절).

### 5.4 복구 기준점 뒤 복구 시간(계약 D4 사용자 결정 2026-10-21)

- 결정: 주기 체크포인트 없이, 사용자 저장이 성공하면 저장 바이트를 복구 기준점으로 두고 복구 때 그 뒤 편집만 재적용한다. 재적용 2 s 기준은 기준점 이후 편집에만 적용한다(구현 `docs/m5-followup.md` 1·3절).
- 측정: `node tools/bench/recovery-time.mjs <코퍼스>/arxiv-2609.10511.pdf 2 100 10`. 3쪽(쪽 콘텐츠 1.2 MB)에서 서로 다른 문단을 차례로 100건 고치고(편집 가능 문단 10개 → 이후 블록 재편집), 90건째 뒤에 저장, 저장 뒤 10건. 복구는 새 세션에서 뷰어 복구 계층처럼 한 건씩(`replayEdits([op], { more })`) 재적용하고 그 쪽을 렌더한다. 서버 Node v22.18.0, 2회(1회째는 다른 측정과 동시 실행, 표는 2회째 load average 3.3).

| 복구 방식 | 연 바이트 | 재적용 편집 | 열기 ms | 재적용 s | 쪽 렌더 ms | 합계 s | 쪽 텍스트 = 원래 세션 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 원본 + 전체 로그(기준점 없음, 이전 방식) | 원본 | 100 | 0.6 | 29.7(1회째 30.8) | 70 | 29.8 | 같음 |

- 기준점 복구는 재적용 편집 수에 비례해 줄었다(100 → 10건). 다만 1.2 MB 쪽 10건은 2 s 기준을 넘는다(편집 1건당 약 0.34–0.38 s: 재적용마다 그 쪽 추출·원본 연결·레이아웃을 다시 계산). 이런 쪽에서 2 s 안에 드는 저장 뒤 편집 수는 약 5건이다. 기준은 결정대로 두고 결과만 기록한다(`docs/m5-followup.md` 7절 남은 일).

## 6. 지원 문서 크기 상한 안내 값(리스크 8, core 값)

- `supportedInputBytes(method = 'full', baseHeapBytes = 22 MiB)`: 이미지 위주 문서(원 스트림 ≈ 입력, 객체 수·객체 크기 0)를 열자마자 편집 후 저장할 때 예상 피크가 상한을 넘기 시작하는 입력 크기. `SUPPORTED_INPUT_BYTES` = 790 MiB(전체), 증분 750 MiB.
- 실측 대조: 합성 이미지 1,000쪽(750 MiB) 전체 저장 성공(최대 1,430 MiB), 1,100쪽(826 MiB) 보기 3쪽 이상 실패.
- 뷰어 사용(S3): `OpenResult.byteLength > SUPPORTED_INPUT_BYTES` 이면 열 때 "편집·저장이 실패할 수 있음" 안내. 저장 직전 판정은 planSave `heap.level`. 이 값은 pdf-ops 에서 export 되고 core 가 다시 export 하지 않는다(core `index.ts` 는 S1 담당 파일 밖, 8절).
